## 2026-04-18 大規模改修から得た教訓

### 互換ラッパーの削除判断は慎重に
- `src/render.py` は単なる再エクスポートに見えるが、`.github/workflows/daily.yml` と
  `tests/test_refactor_compat.py` が公開API として依存していた。
- 削除前に必ず grep と CI 設定を両方チェックする。
- **ルール**: 「単なる互換ラッパー」と見えても、呼び出し元が以下3点にあるか確認する
  1. テストファイル（名前に compat/wrapper/api など）
  2. CI ワークフロー（`.github/workflows/*.yml`）
  3. CLAUDE.md や README のコマンド例

### SQLite FTS5 の初期バックフィルは `rebuild` を使う
- `content='articles'` で外部コンテンツ同期モードの FTS5 仮想テーブルに対し、
  `INSERT ... SELECT` で初期化しようとしたが検索が空を返した。
- 正しくは `INSERT INTO articles_fts(articles_fts) VALUES('rebuild')` コマンドを使う。
- **ルール**: FTS5 を content='<table>' モードで作ったら、初期データは必ず rebuild で投入する。

### FTS5 の unicode61 トークナイザは日本語の分割が弱い
- 「セキュリティ」で検索するとヒットするが、分かち書きされないため複合キーワードに弱い。
- 検索UIは title/title_ja/snippet の JS 側 AND 絞込で代替し、FTS5 は将来の高度検索に温存。

### render_main.py 全面分割は範囲外
- 5091行の HTML テンプレート文字列を含む巨大モジュールを一気に分割するのは危険。
- 新規コード（RSS/検索）を別モジュールに切り出すことで分割パターンを確立し、
  既存コードの分割は「変更したい機能に触れるついで」に少しずつ行う方が現実的。

### pre-existing テスト失敗を自分の変更と混同しない
- 作業中に `test_opinion_page.py`・`test_docs_asset_paths.py` が落ちたが、
  `git stash` で base を検証したところ本作業前から failing だった。
- **ルール**: 改修着手前にまず `pytest` を1回走らせ、ベースラインの green/red を記録する。

### Windows での日本語ファイル読み込みは `PYTHONUTF8=1` が必須
- pytest 実行時に cp932 エンコードで UnicodeDecodeError / 表示崩れが発生。
- ローカルでは環境変数 `PYTHONUTF8=1` を付けるか `sys.setdefaultencoding` 相当で回避する。

## 2026-04-24 世界ニュース欠落事案から得た教訓

### LLM 入力ピックは region×kind でバランスする
- `pick_topic_inputs` が `published_at DESC` 単純順だったため、日本の最新 news が
  大量にあると global/news が後回しになり、1日予算内で処理されずに滞留した。
- 結果、`importance > 0` でフィルタする render 側で世界ニュースが3件のみ表示に。
- **ルール**: トピック優先度は「新しさ」単独ではなく「バケット（region×kind）横断の
  ラウンドロビン」で決める。バケットは `ROW_NUMBER() OVER (PARTITION BY bucket)` で
  各バケット最新→2番目→…の順に並べ、ORDER BY rn ASC で横断する。

### LLM 未処理の蓄積を可視化する
- `pipeline_report.py` は未生成トピック総数しか出していなかったため、
  「global だけが滞留している」構造的偏りに気付けなかった。
- **ルール**: バケット別メトリクスを毎日出力する。閾値超過で WARN を出す。
  サイレントな劣化（特定バケットだけ生成されない）を検知する。

### 互換のためクエリはスキーマ差異を許容する
- テスト用 in-memory DB は `articles.region` カラムが無い簡易スキーマのため、
  新クエリで `a.region` を直接参照するとテストが落ちた。
- **ルール**: スキーマ依存のクエリは `PRAGMA table_info()` でカラム存在確認し、
  式を動的に差し替える。これにより古い DB・簡易テスト DB との互換を維持できる。

## 2026-05-20 未来予測パイプライン全面オーバーホールから得た教訓

### LLM 翻訳系は空応答を必ず防御せよ
- `_translate_to_ja` (forecast_generate.py) が稀に空文字を返し、
  `_localize_prediction_item` がそれで title を上書きすることで
  本番レポートに「### 1. （タイトル無し）」が複数件出ていた。
- **ルール**: LLM翻訳・正規化を文字列フィールドに適用する全箇所で
  `result = llm_call(x); field = result if result.strip() else x` を徹底する。
  これを横断適用するため `_safe_translate` のような薄いラッパー1関数を作って
  そこを単一の通り道にする方が、後の改修コストが低い。

### パイプライン下流モジュールは上流の出力欠陥を「検知」する責務を持つ
- forecast_verify が title 空のアイテムを LLM に渡す際 `- : 本文...` という
  入力を作り、LLM が解析放棄して verdict_json が空配列 `[]` で保存され、
  以降のレポート的中率がほぼ全件 None になっていた（67件中 40件が破損）。
- silent に空配列で上書きする設計は障害を見えなくし、データ的中率の劣化を
  気付かないうちに広げる。
- **ルール**: 下流モジュールでは「上流の出力欠陥」を `None` などで明示的に
  区別して伝搬し、既存データを空で上書きしない。リトライ失敗時は **既存判定を
  保持** する保守的選択をデフォルトとする。

### 文字列ベースの enum は最初から内部キー+表示名分離で設計する
- `HORIZONS = ["1週間後", "1〜6ヶ月後", "1年後"]` のキー文字列が
  forecast_generate / forecast_verify / DB の horizon カラム / parser まで
  横断して使われており、リネームのコストが膨大（互換マップ運用）。
- 表示名と内部キーは設計時に分離するか、最低でも単一の場所に enum 定義を
  集約しておくべきだった。
- **ルール**: 「ユーザーに見せる表示文字列」を内部識別子として共用しない。
  enum 風の文字列を複数モジュールが参照する場合、定義は1モジュールに
  集中させ、表示用ラベルマップを別に持つ。

### 「1呼び出しで複数の独立出力を要求する」設計は失敗時の全滅リスクを必ず見積もる
- 3 horizon を1回の LLM 呼び出しで生成する設計は理論上効率的だが、
  1回の解析失敗で 3 horizon 全滅、品質安定性も下がる。
- 直列+後処理マージ（rapidfuzz による重複除去）の方が、
  失敗局所化・部分成功の積み上げで結果的に安定する。
- **ルール**: 「LLM 呼び出しの粒度を粗くしてバッチ化する」最適化は、
  失敗時の被害範囲と品質安定性を必ず A/B 比較してから採用する。

### 破損データの自動回復は明示的に実装する
- forecast_verifications の verdict_json="[]" + accuracy_score=None という
  破損レコードは「ラウンド1済」とみなされ、修正後も自動再検証されなかった。
- **ルール**: silent failure で生まれたゾンビレコードを後から検出・修復する
  ロジック（_find_verification_targets の「破損は再検証対象」拡張）を、
  パイプライン修正時に必ずセットで入れる。「直したから次から正しい」では
  既存データは救えない。

### Ollama の `/v1/models` は埋め込みモデルとチャットモデルを区別しない
- `_pick_model_candidates` が `/v1/models` の全モデルを順にチャット候補に追加し、
  `bge-m3` / `nomic-embed-text` を `/v1/chat/completions` に POST して連続 400。
  1 verify あたり20分超の暴走を起こしていた。
- **ルール**: ローカル LLM ホストから取得したモデル一覧をフォールバック候補に
  使う場合、必ず**用途（chat / embed / vision）でフィルタする**。Ollama API には
  メタ情報がないので名前パターン（bge / nomic-embed / embed / e5 / gte 等）で
  ヒューリスティック判定し、誤判定時は環境変数で上書き可能にしておく。

### LLM 解析失敗は raw 応答の先頭をログに残せ
- `_call_verify_llm` が「JSON 解析失敗」と言うだけで応答内容を捨てていたため、
  原因がモデル選択ミス（埋め込みフォールバック）か応答品質劣化か切り分けに
  E2E 実行を何度も繰り返す羽目になった。
- **ルール**: LLM 出力を構造化解析する箇所で失敗ハンドラを書くときは、
  raw 応答の先頭 N 字を必ず WARN レベルでログに出す。デバッグ可観測性は
  パース堅牢化より優先順位が高い。

### Ollama OpenAI 互換エンドポイントで `response_format` を試行的に付けない
- `response_format={"type":"json_object"}` を「受理されなければ通常応答に戻る」と
  期待して付けたが、gpt-oss:20b では応答品質が逆に悪化し JSON 解析が3連続失敗した。
- **ルール**: OpenAI 互換だがバックエンドが Ollama の場合、`response_format` は
  「黙って無視される」のではなく「黙って品質劣化させる」可能性がある。実環境で
  A/B を取ってから本採用する。先に system prompt の「JSON のみ」指示で十分なことが多い。

## 2026-05-27 Phase 5 品質チューニングから得た教訓

### 「ニュース重要度トップ」を文脈に放り込むと事件・テロ系に乗っ取られる
- `_aggregate_topic_perspectives` が importance>=50 で重要度順だけにしたら、
  数日のうち2日で「ホワイトハウス周辺発砲事件」「軍事輸送」が3視点分析を占拠した。
  予測は AWS/Azure/原油市況で、3視点だけが事件分析という乖離レポートが出力された。
- **ルール**: 横断トピックを LLM 文脈に注入する際は **カテゴリ allowlist 必須**。
  「重要度順 + 全カテゴリ」は、サイト主旨と関係ない突発ニュースで簡単に侵略される。
  サイトのコンテンツ範囲を allowlist で固定し、突発の事件で読者に提供する文脈を
  汚染しないこと。

### LLM が守らない自己申告フォーマット（[推定] プレフィックス）に依存しない
- T4 で SYSTEM_PROMPT に「ニュースに明記されていない数値は [推定] を付ける」と
  指示したが、gpt-oss:20b は1週間まったく守らなかった（0件）。一方で T10 の
  ポストプロセス検証 (`_validate_numeric_claims`) は12件/レポートも検出。
- **ルール**: LLM の自己申告フォーマット（「○○の場合は ◯◯ を付ける」）は守られない
  前提で、ポストプロセスでの検出・補正をデフォルトで実装する。「言ったから守る」は
  ローカル LLM では期待しない。

### ⚠ 警告ラベルの過剰使用は情報価値を毀損する
- `⚠ 出典未確認の数値: 90ドル, 0.5ドル, 5%, 10万, 200社, 55%, 30%, 20M, 150社…`
  のように12個並ぶと「全部信用ならない」と見えて、予測本文すら読まれなくなる。
- 検出ロジック自体は正しくても、**警告対象を意図的に絞らないと UI 上のノイズになる**。
  パーセンテージは「予測として推定するのが当然」なので警告対象外、社数・金額・
  カウント値のみを「ニュース原文で言及があるべき具体数値」として警告対象に絞った。
- **ルール**: 自動検証警告は「読者が知りたい情報」と「読者を不安にする情報」の境界を
  意識して粒度を調整する。検出可能なものを全部出す ≠ ユーザー体験が良くなる。
  バッジ文言も `⚠` より `📊 [推定値]` のようにニュートラルにする。

### タイトルの単純切り詰めは句読点まで読まれない見出しになる
- `prediction[:40]` フォールバックで「日本のO」「電気SUVを発売し」のように文の途中で
  切れた見出しが量産された。読者は「O？何の話？」と混乱する。
- **ルール**: ユーザーに見せる短縮テキストは句読点（。.!?、,）優先のスマート切り
  詰め関数を共通ユーティリティ化し、全箇所で使う。`s[:N]` は内部処理のキー生成
  くらいでしか使わない。

### LLM の自由生成は「タイトル ≒ 本文」の冗長を生む
- title="ブレント原油先物は来週までに2％上昇する見込みです。"
  prediction="ブレント原油先物は来週までに2％上昇する見込みです。"
  という丸ごと同じ文を2回出すレポートが量産された。LLM の自由度を絞らないと、
  「タイトル＝要約、本文＝詳細」の役割分担を守らない。
- **ルール**: title と prediction（要約 vs 本文）のような階層を持たせるなら、
  プロンプトでの指示だけでなくポストプロセスで重複検知して短縮する仕組みを入れる。
  そうしないと冗長な情報が読者の認知資源を浪費する。

### 本リポジトリは複数プロセスが並行して更新するため、着手前に必ず未コミット差分を確認する（2026-07-13）
- Phase 2（`perspective_digest` の render_main.py 表示実装）着手前に `git status` / `git diff --stat` を
  確認したところ、依頼書には「未実装」と書かれていた表示ロジックが**作業ツリーに既に実装済み**だった
  （render_main.py だけで842行差分、他に十数ファイルが未コミットで変更されていた）。
- 原因: 本リポジトリは `.github/workflows/daily.yml`（夜間パイプライン、`daily update (local LLM)` コミット）や
  他の並行 Claude セッションが同じ作業ツリーに書き込むため、git log（コミット履歴）と実際のファイル内容が
  乖離しやすい。todo.md の「残タスク」記載も、別プロセスが実装を終えても更新されないまま古い記述が残ることがある。
- **ルール**: このリポジトリで作業する際は、todo.md の記述を鵜呑みにせず、着手前に
  `git status` / `git diff --stat <対象ファイル>` で実際の作業ツリーの状態を確認する。
  「依頼された実装が既に存在するかもしれない」という前提で調査してから着手すること。
  実装済みだった場合は、検証・テスト補強・dogfooding・記録更新にスコープを切り替える。

## 2026-07-13 プロジェクト全体改善で得た教訓

### .gitignore の許可リスト方式は「新規出力の追加漏れ」を静かに起こす
- **事象**: `docs/*` を除外して `!` で個別許可する方式のため、後から追加された docs/topic・entity・diff・exec・api・search 等が git 未追跡のまま7ヶ月近くローカル生成止まりになり、本番（GitHub Pages）では404だった。誰も気づかなかった
- **再発防止**: 新しい出力先を追加するときは必ず .gitignore の `!` エントリを同時に更新する。`tests/test_docs_asset_paths.py::test_gitignore_allows_generated_pages_publish` が公開対象の網羅をチェックするので、出力先追加時はこのテストにもエントリを足す

### 機能を廃止するときはテンプレート・ヘルパー・テストも一緒に消す
- **事象**: 意見ページ廃止（7fafd026）の際、ページ生成呼び出しだけが消され、OPINION_HTML テンプレート＋ヘルパー22関数（計1,064行）と test_opinion_page.py（テスト失敗12件の主因）が残置され、半年間「pre-existing 失敗」として持ち越され続けた
- **再発防止**: 機能削除の際は `grep` で関連シンボルを洗い出し、死コードとテストを同一コミットで削除する。「テストが失敗し続けている状態」を既知として放置しない（真の regression が埋もれる）

### 生成物の無制限蓄積には最初から retention を付ける
- **事象**: topic_snapshots が全トピック×日次スナップショットで150万行/480MBまで肥大（利用者の diff_view は直近2日しか見ないのに）。DBバックアップも498MB×3世代が無管理で残置され計1.5GB圧迫
- **再発防止**: 「毎日追記する」テーブル・ログ・バックアップを新設するときは、その場で保持期間（日数 or 世代数）を決めて削除処理を同時に実装する

### 部分文字列マッチは日本語混在コーパスで大量の誤マッチを生む
- **事象**: エンティティ抽出が小文字部分一致だったため、鉄鋼系記事で "Meta"→"metal" 等の誤マッチが発生。リンクの約7割（12,145中8,472件）が誤りだった
- **再発防止**: ASCII 語の照合は必ず単語境界（）付き正規表現にする。2文字以下の alias は登録しない

## 2026-07-28 トップページ軽量化実装セッションで得た教訓

### 手動 render.py 実行前に本番スケジュールタスクの実行状態を確認する
- **事象**: トップページ軽量化の実機検証のため `python src/render.py` を手動実行したところ、ちょうど同時刻に "Daily Tech Trend" スケジュールタスクが実行中（dedupeフェーズ、`data/state.sqlite`へ書き込み中）で、`diff.render`/`entities.render`が`database is locked`で失敗した。目的のtech/news/insights_*.json自体は正常に書き出せたため実害はなかったが、タイミングが悪ければより広範囲が失敗しうる
- **再発防止**: `data/state.sqlite`へ書き込みを伴う本番パイプラインを持つプロジェクトで手動 render.py（または同様のDB読み書きスクリプト）を実行する前は、必ず `Get-ScheduledTask -TaskName "Daily Tech Trend"` 等でState（Running/Ready）を確認する。他プロジェクト（GPU/Ollama起動前チェック等）で既に定着している「起動前に稼働状況を確認する」習慣を、DBファイルの読み書き競合にも適用する

## 2026-07-29 render_main.py 可読性改善（関数分離）で得た教訓

### 巨大関数からのブロック抽出は「1回だけ計算されるスカラー変数」を見落としやすい
- **事象**: `main()`から「ops用データ取得」ブロック（約170行）を`_build_ops_page_data()`として関数分離した際、ブロック内で計算される`primary_ratio_threshold`（一次情報比率の閾値、後続で3箇所からops.html描画に使われる）を戻り値dictに含め忘れた。`ops_stats`等のリスト/辞書型変数は grep で使用箇所を洗い出す際に見つけやすいが、`if/else`の判定にしか使わず後続コードでは「結果」だけが参照されがちな単純スカラー変数は見落としやすい
- **さらに重要な発見**: この抽出ミスは`python -m pytest -q`（236件）では一切検出されず、`python src/render.py`（実データでの本番描画パス）を実行して初めて`NameError`として発覚した。既存のpytestスイートは`main()`のops.html描画パスを実データでE2E検証していないため
- **再発防止**:
  1. 巨大関数からブロックを抽出する前に、対象ブロックで**新規に定義される全てのローカル変数名**を機械的にリストアップし（代入文の左辺を全部grep）、抽出範囲外（関数の残り部分）でそれぞれが参照されていないか確認する。「戻り値として使う集計結果」だけでなく「計算に使った閾値・設定値」も同列に洗い出す対象にする
  2. pytestが全greenでも、`main()`のような「実データ＋全ページ描画」を1回のテストで通しで検証していないコードベースでは、リファクタのregressionを検出できない。**render.py（または同等のエントリポイント）を実際に実行する検証を、pytestとは別に必須の検証手順とする**（今回はこれで発見・即修正できた）

### 1. SQLiteでCTEを相関サブクエリの中から参照すると、対象行ごとにCTE全体が再計算される
- **事象**: `thread.py` の `mark_news_representative_articles` が単独で**491〜855秒**を消費していた。
